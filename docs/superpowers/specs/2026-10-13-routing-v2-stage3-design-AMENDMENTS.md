# Amendments to the stage-3 design (found while writing and validating the plan, 2026-10-13)

The spec `2026-10-13-routing-v2-stage3-design.md` was approved on 2026-10-13. Writing the plan meant building every module in a shadow copy of the repository and testing it (mutation checks, the full suite, a byte-level flag-off comparison). That turned up the points below. None of them changes a pre-registered statement, a bar, or a decision rule (sections 7 and 8 of the spec stand; A-15 and A-16, added on 2026-10-14 after the first dev run, change the mechanism and are discussed in their own section below); they make the spec precise where it was silent, or replace a mechanism by one that is safer. Each is built into the validated assets of the plan (`docs/superpowers/plans/2026-10-13-routing-v2-stage3-assets/`).

| ID | Spec says | Now | Why |
|---|---|---|---|
| A-1 | A spawned or extended expert starts with its cluster as its first window (4.3). | Windows are created lazily from the samples an expert is trained on; until a window holds `set_gate_min_ref` rows the expert's stored prototypes stand in. | That is what the measuring spike did (`spike_set_gate.py`), so the dev effects describe this behaviour; it needs no hook inside `_handle_cluster`. |
| A-2 | `PhyloMoE.predict(x, ctx=None, groups=None)` (5). | A separate method `predict_grouped(x, groups, ctx=None)`; `predict` is not touched. | `tests/growmoe/test_gm_phylo.py::test_phylo_signatures_no_gt` pins the signature of `predict` (no side channel into the pool). Group ids are opaque, caller-chosen integers (a document, a session, a batch); the benchmark builds them from single-source test chunks and says so. With the flag off, `predict_grouped` returns `predict(x, ctx)` itself. |
| A-3 | New optional field `StepRecord.set_verdict` (4.3). | `StepRecord.meta["set_verdict"]`, present on every `observe` call when `set_gate` is on (including the bootstrap calls: `None`), absent when it is off. | `StepRecord` already has `meta`; no shared dataclass changes, flag-off records stay equal to today's. |
| A-4 | Section 6 lists the config. | Two more fields, `set_gate_min_labels` (8) and `set_gate_max_rows` (512), and `PhyloCfg.__post_init__` validation: a level that the permutation count can never reach (smallest p-value 1/(1+perms) above the level) is refused, as are unknown names and non-positive sizes. | A test that can never reject silently turns the gate into "everything is known"; a batch of thousands of rows would make the MMD kernel blow up memory. |
| A-5 | One generator per decision (4.3). | One generator per (decision, expert, reference), keyed by (seed, step, expert id, reference index) through `numpy.random.SeedSequence`; window splits use their own key. | A decision no longer depends on the order experts are listed or on early stops; the same pool state gives the same verdicts. |
| A-6 | Breaker pauses "for `pause` steps" (4.3). | The set level is off while `step < opening_step + pause` (so `pause - 1` further batches), the memory is cleared at opening, and only batches with at least 90 % of their samples accepted feed it. | Matches the spike's code; stated exactly so the counters mean one thing. |
| A-7 | `SourceWindows.refs()` (4.2). | Adds `ref_pairs()` (rows, mean) with the concatenation and the mean cached until the window changes, and `n_samples()`; stored batches and tested sets are cut to `set_gate_max_rows` rows (a random subset) so memory and time are bounded. | With hundreds of experts the candidate scan must cost O(experts x references x d), not O(rows); otherwise stage 3 would undo the saving of stage 2. With the default batch of 64 nothing is ever cut. |
| A-8 | A merged expert takes the union of the windows (4.3). | Built exactly so (`SourceWindows.merge_from`, newest `max_windows` kept by last-push step) and tested with a real merge. Source windows count as stored vectors in `pool_report` (`stored_vectors`, hence `memory_bytes` and the matched-capacity kNN). | The spike did not merge windows (survivor kept its own); the union is the safer rule and the memory accounting stays honest. Flag off: no windows exist, so nothing changes. |
| A-9 | S3-4 "on every stream"; S3-5 "known single-source batches". | S3-4 is evaluated on the ten regular streams (the label-sorted F-15 is reported, where the breaker is what is being tested). S3-5 pools the nine single-source streams (all but OV-0.3-MIXED); its denominator is every batch labelled "known" (batch 3 or later of a first visit, or any batch of a revisit), whether or not a test ran, as in the spike. | Makes the denominators explicit. |
| A-10 | S3-9 "bit-identical to today". | Operationalised by golden fingerprints (`research/growmoe_results/rv2c/golden.py`): 20 (configuration, stream) runs, integers only, recorded on the code BEFORE any stage-3 edit and checked after every task; the in-suite test checks three of them, the report checks all twenty. The file must stay byte-identical after the edits (verified in the shadow tree). | The only way to prove "unchanged" is to compare with an unchanged copy. |
| A-11 | Breaker tuning on dev seeds (8). | Run as a lazy successive halving: all four settings on the two pressure streams (label-sorted F-15, OV-0.0; seeds 100-102), ordered by experts (ties to the larger memory), then the expensive "never fires" check on OV-0.85, OV-0.6, S1, S2-30, F-30 (seeds 100-109) for the best setting first, the next only if it fires. | Same selection rule as the spec, a fraction of the compute. |
| A-12 | Counters and events (4.3). | Counters: tests, early_stops, perms, novel, known, override, paused, breaker_opens, window_splits (no wall-clock; `observe` seconds are measured by the runner). Events: `set_novel`, `set_override`, `breaker_open`. | Names fixed. |
| A-13 | Group evaluation on pools of both arms (7). | `group_vote` is switched on after training, in the evaluation only, so the group answer and the per-input answer come from the same trained pool. `evaluate_groups` refuses a pool whose flag is off. | Pairs the two answers exactly; guards against silently measuring nothing. |
| A-14 | Arms use "the stage-2 cascade as adopted". | `A_vote` pins `set_gate=False, group_vote=False` explicitly, and so do `golden.py` and the pool tests. | If a default is flipped later these must keep their meaning. |
| A-15 | A batch the set test calls new is acted on at once: its accepted samples go to the probation buffer (4.3). | **Persistence** (config `set_gate_confirm`, default 2; 1 = the first build). The first doubtful decided batch of a run is HELD whole: its accepted samples are not trained or assigned, its per-sample-flagged samples wait with them instead of entering probation. If the NEXT decided batch is doubtful too, the held samples join its cluster and the pool acts as in the spec; if the next decided batch is known, the held samples are dropped (a false alarm costs one skipped batch and nothing else). A hold expires after 3 steps; batches without a decision (fewer than `batch_vote_min` accepted samples, or the gate paused) do not change the count; the circuit breaker is fed the raw verdict. Incompatible with `no_probation` (refused). | The first dev run (seeds 100-109) failed two guard statements: a false "new as a set" verdict on a KNOWN batch (level 0.001 per test) sends that batch to probation and the evidence test then often spawns a duplicate expert (F-30 -0.48 [-2.62, +1.66], OV-0.0 -1.02 [-2.56, +0.52], both S3-2 PARTIAL). With persistence: F-30 -0.17 [-0.54, +0.20], OV-0.0 +0.03 [-0.13, +0.18], S3-1 to S3-5 PASS on the dev seeds, at the price of one batch of delay on a really new regime (OV-0.6 +17.26 instead of +18.12, OV-0.85 +5.91 instead of +6.42). Details and the two weaker variants tried first (skip the batch; hold only its accepted samples, which left duplicates): `research/growmoe_results/rv2c/SENS_RV3.md`. Approved by the user on 2026-10-14. |
| A-16 | The group veto keeps an input's own choice when its exact p-value under the group's expert is below `q` (5). | Its own level `group_veto_q`, default 0.2 (`q` stays 0.02 for the per-sample gate). | The dev sweep (pools of the persistence variant): at 0.02 the 50/50 mixed groups of S1 lose 5.83 points against answering each input alone (bar: -5.0, S3-7 PARTIAL); at 0.2 they lose 1.58, while the pure groups keep most of their gain (OV-0.85 +9.08 instead of +12.66, OV-0.6 +0.90). A higher level means more inputs keep their own expert, i.e. the group vote moves fewer inputs. Approved by the user on 2026-10-14. |

## A-15 and A-16 are different in kind (read before relying on the dev numbers)

A-1 to A-14 make the spec precise or safer without changing what the mechanism does. A-15 and A-16 change the mechanism (a held batch; a higher veto level). They were chosen AFTER the first dev run, on the dev seeds 100-109 (an exploratory, not pre-registered study: `sens_dev.py`, `SENS_RV3.md`), so the dev numbers above are what the choice was fitted to. The pre-registered statements S3-1 to S3-9, their bars and the decision rule are unchanged, and the fresh confirmatory seeds 60-79 have not been touched; the amended mechanism is frozen (config defaults, hashes) before that run. What follows from this:

- The first dev run, its breaker choice and the trace output are superseded. The breaker grid is chosen again under the final mechanism (the old files are kept in `research/growmoe_results/rv2c/_before_confirm/`, not deleted).
- `set_gate_confirm=1` is the first build bit for bit (a fingerprint test pins it), so every earlier stage-3 result stays reproducible with that one setting.
- The product code reproduces the exploratory persistence arm run for run (same accuracy, expert counts, verdict counts and group results on dev seeds 100-102, checked in a shadow copy); `sens_dev.py` is historical and pins `set_gate_confirm=1` and a veto level equal to `q`, so that its own arms keep their meaning.
- Not part of these amendments: the component verification (`2026-10-14-growmoe-component-verification-audit.md`, CVA-1 and CVA-1B) found that the probation evidence test, which decides on a spawn once the set gate has handed it a cluster, is not calibrated (a cluster drawn from an existing expert's own regime is called new 0 to 2 % of the time at 32 to 64 points, 5 to 12 % at 128 and 33 to 52 % at 256). Persistence builds its first cluster from two batches (about 128 points), but only after TWO consecutive batches the exact set test called new at level 0.001, so the clusters it evaluates are almost always truly new; a spawn rule based on the same exact permutation test is the candidate for a later stage 4 with its own pre-registration and is NOT enabled here.

## Found by the real-text work done in parallel (not an amendment, a standing caution)

On the first real class-incremental stream (banking77, M5) today's pool builds 1 to 3 experts for 6 regimes and, in Gemini's M5-B output file (dev seeds, tuned and scored on the same seeds, NOT yet audited by Claude), a tuned single replay network scores about 12 points above it, with oracle-routed experts also below that network (details go into the lab notebook after the audit). The stage-3 statements are pre-registered on the synthetic streams, where the effect was measured; the real stream is a reported arm. No document may say that stage 3 helps on real text until the reported arm shows it.
