## 1. What was measured (read-only evidence, do not redo)

`m1/diag_gpu_probe.py`, output `results/m1/diag/gpu_probe_2026-11-03.json` (8 s, RTX 3060, torch 2.6.0+cu124; CPU side 2 threads on logical 8 and 10; real shapes: d 128, 64 new + 64 replay samples, 64 classes, Adam lr 3e-3, fp32). ## 2. What to build

### 2.1 Scope
Arms **A3, A3-2, A4, A4-2, A6, A8** on beds B1 (N = 10, 30, 100), B2, B3seq, B3mix, B3drift, at **exactly the operating points of the frozen tuning files** `results/m1/tuning/<bed>.json` (read through the same `tuning` entry as `m1.queue`; store the same `tuning_ref`). No re-tuning for the GPU (a stated limit: a GPU could afford wider networks). Pool arms and the other baselines are not repeated.

### 2.2 Same computation, other device
Build each arm on the CPU exactly as `m1.arms.build_arm` does (same initial weights, same NumPy sampling streams), then move what computes to the GPU: the network, the optimiser state, the replay reservoir or joint buffer (A8), the A6 projection and its accumulators (keep float64 where the CPU code uses float64). Disable TF32 (`torch.backends.cuda.matmul.allow_tf32` and `torch.backends.cudnn.allow_tf32` False), no bf16/fp16 (quality must not drop), set `CUBLAS_WORKSPACE_CONFIG=:4096:8` before CUDA initialises and `torch.use_deterministic_algorithms(True, warn_only=True)`. Store these settings in every record. Batches come from the host bed: **the host-to-device copy of each batch is inside the timed region**, and an answer call is timed as `arm.predict(x_host)` including the copy in, the copy of the probabilities back, and a final `torch.cuda.synchronize()`. Read `costlab/timing.py` (`time_callable(device=...)`) and report whether it synchronises; every wall-clock read in your own loop is preceded by `torch.cuda.synchronize()`. A warm-up (CUDA context, cuBLAS handle, one throw-away step on a net of the same width) happens before the first timed observe; record its duration in `warmup_s` and keep it out of `wall_clock_total`.

### 2.3 Record
Schema 1.2.0 of `m1/cell.py`, `profile` "full", plus: `device` "cuda", `gpu` (name, driver, torch, cuda, the NVML state of `costlab.energy.gpu_state` before the cell: utilisation and memory used, because the Windows desktop already uses the GPU), `vram_peak_bytes` (`costlab.memory.peak_memory(device="cuda")`), `numerics` (the flags above), `warmup_s`. Counted multiply-adds are device independent: compute them on the CPU copy with the same functions as `execute_cell` and check they equal the CPU cell's whenever a CPU cell exists (report every mismatch). Cells go to a different folder from the CPU cells (`--out`, default `results/m1/scored_gpu` for the report split, `results/m1/dev_gpu` for dev) with the same file names, so the two can never be mixed by accident. You may NOT edit `m1/cell.py`: write `execute_gpu_cell` in the new module, import every helper you can (`accounting_block`, `save_cell_record`, `compute_tuning_ref`, `cell_filename`, `is_valid_cell_record`, `read_pool_budget`, `read_pool_macs`), and guard the duplicated part with a test: with `device="cpu"` your function must return the same record as `execute_cell` for the same tiny bed and arm (accuracy, forgetting, memory, counted multiply-adds, config, per-regime accuracy equal; timing, `device` and the added fields excluded). Cleaning up the duplication is a later job after the scored run, not yours.
