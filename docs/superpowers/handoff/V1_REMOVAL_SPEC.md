## 0. Why, and what the question is
Read `docs/roadmap/MILESTONES.md` (probe P2), `docs/roadmap/V0_WALKING_SKELETON.md` (section 5, V1) and `docs/roadmap/RESEARCH_DIGEST.md` (section 2, unlearning). The user wants knowledge that is unnecessary or proven wrong to be removed, and our design suggests removal can be EXACT where components are isolated, which published MoE unlearning methods do not claim. The user's standing rule (2026-10-16): no eviction without certified redundancy; sharing, not dropping; averaging only once validated. The question of this job is a measurement: **for each component that can have seen a removed class, is removal exact (equal to a model that never saw the data), approximate (measured difference) or impossible without a code change, and what exactly is the change?** The answer may be disappointing; report it as measured. "Exact" has one definition here: float64, absolute difference at most `TOL_EXACT = 1e-6` on every stored statistic, weight and probability, and identical predictions.

Two binding facts about the machine: a long CPU run (the scored run of M1) is in progress and imports `m1/`, `growmoe/`, `unimoe/`, `costlab/` fresh for each seed, so you create NEW FILES ONLY and never change the behaviour of existing classes except by instance-level wrappers inside your own files; its timings must not be disturbed, so all CPU work is pinned to logical processors 8 and 10 with 2 threads (`costlab.env.fixed_threads(n=2, cpus=[8, 10])`), each command under 2 minutes (design experiments as separate commands that write one JSON each), never `tests/m1`, `m1.queue`, `m1.tune`, `m1.report`, `scored_run.sh`.

## 2. Part A: exact downdating of the closed-form heads (`v1/downdate.py`)
Implement `remove_classes(model, labels, data=None)` for each of: `ClassMean` and `KnnMemory` (`growmoe/memory_baselines.py`), `MahalanobisProto` (A5b) and `RandomFeatureRidge` (A6) (`m1/baselines_extra.py`), and a NEW class `ExactLda` that keeps per-class sufficient statistics (count, sum, scatter) and computes the shared within-class covariance from them (the batch estimator, not the recursive one). Removal means: subtract or delete what the removed classes contributed. `RandomFeatureRidge` needs the removed samples again (its Gram matrix G is not class-separable): the function takes `data=(x, y)` of the removed samples and downdates `G -= phi^T phi` and zeroes the class column of `C`/`B`; say so in the audit. For each model, removal set and seed: train on everything, remove, train a fresh model without R, and report the maximum absolute difference of every stored statistic and of the solved weights, the maximum difference of the predicted probabilities on the test sets of the retained classes, and the share of identical argmax predictions. Also measure how far `StreamingLDA` (A5a, the recursive running covariance) is from `ExactLda` on the same data (covariance difference, accuracy difference on the test sets) and whether A5a can be downdated at all (its covariance update depends on the arrival order and the running class mean, so subtracting a class is probably not exact: measure it, do not assume it).

## 3. Part B: removal in the pool with a certificate (`v1/pool_removal.py`)
The pool is the V0 pool: `v0.system.build_v0(bed)` (UniPool with the ULDA switches). Read `growmoe/pools/phylo.py`, `unimoe/pools.py`, `unimoe/heads.py`, `growmoe/pools/base.py` (`ExpertRecord`, `Reservoir`, `remove_expert`, lineage), `growmoe/router.py`, `growmoe/signature.py`, `growmoe/sources.py`, `growmoe/conformal.py`, `growmoe/competence.py`, `growmoe/probation.py`, `growmoe/setgate.py`, `growmoe/settest.py`, `growmoe/fingerprint.py`, `growmoe/telemetry.py` and enumerate EVERY structure that can hold information from a training example (the list is a hint, not complete: find the rest, name each one in the audit with file and line).
1. **Exposure log.** By instance-level wrappers (no edit of those files) record, for each expert, which labels of R it trained on directly (training batches, replay batches) and which labels sit in its reservoir, its signature, its source windows and its calibration data; close it over lineage (children initialised from a parent, merges, averaging). Report, per removal set and seed, how many experts are directly and indirectly exposed, and how many retained classes live in an exposed expert (the **collateral**: classes lost if the whole expert is dropped).
2. **`remove_labels(pool, labels)`.** Drops every exposed expert, purges the labels from every structure of the retained experts (reservoirs by deleting rows; signatures, source windows, calibration sets, competence and probation windows by whatever is exactly possible; say where it is not), refits the router, and returns a **certificate**: for every component the number of residual traces of the removed labels found by an independent scan (`scan_traces(pool, labels)`, written to look into every structure, not only the ones `remove_labels` touched), its classification (exact, approximate with a measured difference, not removable without a code change) and the experts dropped. The certificate is plain JSON.
3. **Comparison with the never-trained pool.** For each removal set and seed report: accuracy on the retained classes (mean and per regime) of P_full, P_removed (after `remove_labels`) and P_never; the agreement of routing decisions and of argmax predictions between P_removed and P_never on the retained test sets; and the weight difference of every retained expert of P_removed to the expert of P_never that corresponds to it (match them by their founding batch; if they cannot be matched, say so and report the count). Do not expect equality: pool training is order and seed dependent; report what you measure.
4. **Class accuracy after removal:** accuracy of P_removed on the test examples of the removed classes (it must not predict a removed label; report how often it does).

## 4. The audit table (`docs/superpowers/handoff/P2_REMOVAL_AUDIT.md`)
