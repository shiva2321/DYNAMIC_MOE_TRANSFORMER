## Question
Can the gate decide about a whole batch of inputs with a statistical test whose error rate we know, so that regimes the per-sample test cannot tell apart (centre cosine 0.6 and above) are still recognised as new, without crying wolf on batches the pool already knows? And is there anything to gain from answering inputs in groups, or from smarter per-sample arbitration?

## Why we asked it
E-014/E-017/E-019: the per-sample conformal gate is excellent for separated regimes and blind for overlapping ones (at centre cosine 0.85 it flags 1.6 % of foreign inputs); after the batch vote the pool still merges overlapping regimes (OV-0.6 25.1 % against about 48 % for oracle-routed experts). Spec section 6 (stage 3) said: spike first with hard acceptance criteria, abandon if unmet; my first set-level attempt (Fisher combination of per-sample p-values) over-fired in the live pool (72-131 experts for 10 regimes, F-17). The user then asked for a gatekeeper of our own and told us to research the literature and codebases (`research/GATEKEEPER_RESEARCH_2026-10.md`).

## Prediction
Exploratory steps (clean setting, shadow mode, power, arbitration, ordered batches): none written; the aim was to find what works. Integration spike: the spec's stage-3 acceptance criteria, fixed on 2026-10-10 before any set-level code existed: (a) expert counts unchanged (within 0.5) on F-15, S1, S2-5, S2-30, OV-0; (b) at OV-0.6 and OV-0.85 at least 8 experts for 10 regimes and at least +8 points over the vote. (F-30 was not run in the spike; F-15 covers the family.)

## Method (how)
Dev seeds 100-102, batch size 64, the A_vote configuration of RV2-A (steps perm 20 / func 5 / types 200, q 0.02, alpha_spawn 0.01, m_min 32, accept_then_logf, batch vote ON). Every script is in `research/growmoe_results/rv3/`; `README.md` there lists the order of the evidence and which code generation produced which log.
- **A1, clean setting:** per regime a signature on its first-visit data; in-regime batches against foreign batches; centre cosine 0 / 0.3 / 0.6 / 0.85. Statistics against the expert's stored prototypes: the Fisher combination of the owner's per-sample p-values (the naive test), a permutation test on the distance of means, a permutation test on an RBF-kernel MMD, a score-sum bootstrap. 999 random permutations, p = (1 + #{T_perm >= T_obs}) / 1000 (counted in integers).
- **A2 / A2-recent, shadow mode:** the ordinary pool is trained; before every batch the statistics are computed against the batch's best-explaining expert and only logged; reference = stored prototypes, or the owner's last five trained batches.
- **Trace:** `diag_set_gate.py` prints every set-test decision on one stream.
- **Integration:** a patched copy of `PhyloMoE.observe`. After the batch vote the accepted samples (at least 8) are tested as a set against candidate experts; if every candidate rejects, the accepted samples are novel as a set and go to the probation buffer with the flagged ones; otherwise an admitted expert owns them. Generations: 1 candidates = the per-sample gate's owners first; 2 candidates = nearest reference mean; 3 per-expert source windows and the ownership policies own / keep / veto; 4 ownership by label loss; 5 circuit breaker and MMD. Variants compared in `compare_variants.py`.
- **Routing:** `spike_arbitration.py`: per-sample arbitration upgrades; answering a group by the vote of its inputs' own choices, with and without a per-sample veto; pure groups, 50/50 and 90/10 mixed groups, group sizes 8 to 128.
- **Power against batch size:** `spike_power_vs_batch.py`. **Ordered batches:** `spike_sorted_batches.py`.

## Interpretation (what we understood, and on what basis)
Plain words first. Looking at one input at a time, two regimes whose centres are close look alike, so the per-sample test cannot separate them. Looking at 64 inputs at once, the average position of the group differs clearly from the other regime's, and a permutation test turns that difference into an exact error rate; in a clean setting it works perfectly, down to 8 inputs [A, G]. Inside the running pool it failed in several different ways (stored prototypes as the reference, two wrong rules for choosing whom to test, one window for experts that learned several regimes, two wrong ownership rules), each fixable, and the fixes are the design: (1) the reference. The stored prototypes summarise what an expert ever saw, one recent window mixes the regimes an expert learned in turn; testing a batch against such a mixture rejects batches that are perfectly known [B, C, D]. One window per recent source fixes it. (2) Whom to test. The per-sample gate prefers old broad experts to the fresh specialised one, so the expert that should own the batch was never tested and a new expert was spawned for every batch [J]; the candidates must be chosen by the statistic the test uses (the nearest window mean). (3) Who owns an admitted batch. The vote lets the old expert keep absorbing the new regime; the nearest window fixes that but is worse than the per-sample density among heterogeneous regimes (S1); the label loss among the admitted experts is neutral there [D]. (4) At inference the same machinery is not needed: the majority vote of the inputs' own choices already carries the signal, because 64 noisy choices add up; the permutation test adds nothing [F]. The per-sample veto is what makes it safe for mixed groups.

Technical: the permutation p-value is exact under exchangeability of the batch with the reference, so everything rests on that assumption; the failures in B and D are violations of it (a reference that mixes sources), and the label-sorted run [H] is the plain violation. The Fisher combination fails because the conformal p-values of a batch share one calibration set and are dependent (F-17).

## Caveats and what went wrong
- Dev seeds only (3). The design was iterated on those same seeds through five generations, so the dev effects are optimistic by the garden of forking paths; the pre-registered run on fresh seeds (60-79) is what counts.
- Every stream is synthetic with strongly mean-separated regimes; the batch mean separates them so well that 8 inputs suffice. A clean-setting check on three real text sets followed (E-024): the premise holds there, the per-sample gate is even blinder, and about 16 documents are needed for the hardest pairs; the live pool on a real stream is still untested (Q-04). A mean-based statistic is blind to regimes that differ only in higher moments; MMD [I] is the hedge.
- Batches are assumed single-source and random within a source; ordered batches break the set gate [H] (and the whole pool).
- Ownership by label loss needs labels; without them the nearest window costs S1 about 2 points.
- Group answering assumes the caller can group inputs; the groups here are regime-pure test chunks.
- The faster breaker setting (12 batches, 35 %) was chosen after seeing that the first one (30 batches, 30 %) contained only half the damage, and was checked on the same ordered-batch scenario: it needs its own dev tuning in the implementation round.
- A few interactive runs (the "veto" ownership policy, the first S1/OV-0.85 checks of source windows with the own/keep policies) were not saved and are not evidence; they only steered the search.
- Wall-clock overheads were measured on a shared, busy machine and are not claimed; one full permutation test is 32 ms on one busy thread.
- Process slips, all repaired: the float32 permutation p-value made detection at level 0.001 read 0 in the first log (F-23, `spike_set_tests_log.txt` kept as a record); shell-escape slips broke three patch scripts; the circuit-breaker code referred to module globals that the patched `observe` cannot see (NameError, fixed with attributes).
- Abstain events: a batch called new as a set whose cluster fails the evidence test waits in the probation buffer and may expire untrained (2 per run at OV-0.85, 6 on OV-0.3-MIXED); not mitigated.

## Consequence
The design "Gatekeeper v3, a two-level gate" in `research/GATEKEEPER_RESEARCH_2026-10.md` section 6: stage 2 (fingerprint shortlist, in the pre-registered run), stage 3a (set gate while learning) and stage 3b (group answering with the veto), both flags OFF until a pre-registered run on seeds 60-79. Decisions D-21 to D-24. Per-sample arbitration upgrades are not built. Awaiting the user's approval of the design; then spec addendum, plan, hand-off to Gemini after stage 2 is adopted.
